## 目标和边界

模型仍可能生成复杂命令；系统应保证不符合审阅要求的命令不会因重试次数耗尽，进入普通审批后执行。目标是让用户能看清操作、目标和实际执行内容，而非简单限制命令长度。

覆盖 macOS、Linux、Windows，覆盖内置 shell_run、powershell_run、process_run，以及注册为 ShellExecution 的扩展工具。未经可信能力声明的外部 MCP 服务无法获得同等级的命令分析保证，应明确显示能力边界。

可审查性不等于安全性。单个程序、构建工具或脚本也可以产生任意副作用；本计划不声称静态分析能穷尽行为，也不把路径审批当成操作系统沙箱。

## 已确认的现状

- internal/tools/guidance.go 已引导使用 process_run，并要求分开检查、修改和验证；单靠提示不能保证遵守。
- internal/approval/reviewability.go 已基于 POSIX AST 和 PowerShell bridge IR 识别多动作、混合读写、动态目标和部分嵌套解释器。
- internal/app/command_preflight.go 只有一次纠正预算。used=true 后直接放行；Minimal 和 ReviewNever 也跳过检查。
- internal/app/request_session.go 在审批前调用 preflight，是实施新约束的现有入口。
- process_run 的普通字面参数默认被视为 simple，不能据此认定 Python、Node、编辑器表达式或外部脚本内容简单。
- 2026-08-07-command-reviewability-design.md 明确不永久拒绝复杂命令；本计划需要取代这一边界。
- 2026-09-03-write-target-approval-design.md 规定已判定只读免审、临时写豁免和 never 放行。新增结构约束与这些规则的交互必须明确更新文档和测试。

用户提供的下载循环作为回归样例。仅凭审批截图不能断言它是否已经用过纠正预算，或运行的是否就是当前源码版本。

## 设计决策

### 1. 将建议和执行约束分开

新增独立决策：允许进入现有审批、要求重新组织、要求完整脚本审阅。单程序应改用 process_run 属于建议；不透明的复合写入、未解析目标的批量修改属于约束。不能直接把现有 ShouldCorrect 全部改成永久拒绝。

每次调用都重新检查；纠正预算仅控制模型重试，不能控制是否绕过约束。建议每个用户请求最多自动纠正两次；仍不合格时终止该操作并解释原因。预算应线程安全，按请求统计，不因换工具、改写命令或新模型轮次而重置；失败不得触发执行。独立且合格的调用不消耗预算。

默认在 auto、always 及 Minimal 下执行约束；Minimal 只减少提示，不能暗中取消保证。never 保留用户显式关闭审查的语义，并清楚说明此模式不提供可审查性保证。缺少交互终端时，不能完成完整脚本审阅的操作返回明确错误。

### 2. 用结构和实际语义判断，不用字符黑名单

| 情况 | 默认处理 |
| --- | --- |
| 单个程序和字面参数，目标明确 | 进入既有审批；不要求额外确认 |
| 静态证明只读的管道、过滤和查询 | 保持免审，不因长度或多个阶段拦截 |
| 建目录、下载、检查结果混为一条命令 | 要求按目的拆成调用 |
| 固定列表循环执行修改 | 优先要求结构化批量工具或独立调用；不以解析出列表作为整段脚本豁免 |
| 动态写路径 | 先只读解析，再使用字面路径；必要的动态脚本进入完整脚本审阅 |
| 嵌套 shell、动态求值、编码执行、下载后立即执行 | 解析实际载荷；无法确定内容时不得按普通命令放行 |
| 单个构建、测试、安装程序 | 保留直接调用能力，未知副作用走既有审批；不承诺解析其所有子进程 |
| 引用脚本文件或带内联代码的解释器 | 显式标记脚本执行，检查内容可获取性，进入对应分析或完整审阅 |

必要管道不能任意拆开。条件执行、工作目录、环境变量、退出状态和数据流必须保持语义；不由运行时字符串切割器自动拆分原始 Shell。

PowerShell 的 Where-Object/ForEach-Object 脚本块应根据内容判断，不能只看到花括号就拦截。POSIX 的引号内分号也不能计为多个操作。为递归分析设置深度、时间和载荷大小上限，超过上限进入完整审阅，不猜测。

LLM 可辅助解释未知副作用，但不能消除确定性的结构阻断。对于结构合格的调用，保留现有只读判断规则；对于不透明载荷，不能仅凭 LLM 返回 read 越过新约束。这是对旧只读豁免边界的明确收紧，需要独立回归覆盖。

### 3. 提供足够的结构化工具

优先复用现有文件和进程工具，核对建目录、复制、移动等能力缺口后再补齐。process_run 已有 cwd；为实际需要 Shell 的调用增加结构化 cwd，统一审批和执行的路径解析，减少 cd/Set-Location 串联。

增加跨平台下载工具，支持明确的 URL/目标路径列表：

- 由 Go 实现，减少对 curl、wget 和平台别名的依赖。
- 每项输入是具体 URL 和目标路径，逐项生成读来源与写目标；源站读取不能误标为远端修改。
- 审批展示每个文件，批量大小有上限；只有全部目标符合既有规则才可免审。
- 检查 HTTP 失败、重定向和目标路径；复用或一致实现现有私网访问限制，重定向也重新检查。凭据不进入普通日志。
- 明确覆盖策略、超时、大小限制、取消和部分失败行为；使用受控临时文件和原子替换，返回每项结果，不能声称整个批次具备事务性。
- 不自动执行下载内容，也不声称仅凭 HTTP 成功能验证文件来自正确仓库。完整 URL 缺失仍需输入验证或模型纠正。

提示词同步说明工具选择与失败后的改写方式，只作为减少拦截次数的辅助手段。

### 4. 为必要的复杂脚本提供专门审阅入口

不能通过写入临时脚本、改用 python -c/node -e、PowerShell EncodedCommand、sh script、cmd /c 等方式恢复普通单行审批。

完整脚本审阅必须包含解释器、工作目录、参数、完整可展开内容、已知修改目标以及未知副作用说明。审阅绑定实际执行的内容快照和参数；内容变更必须重新审阅。运行时应执行已审阅的快照，而不只是检查原文件后重新打开存在竞争窗口的路径。

快照不能冻结被导入文件、外部服务或所有子进程；界面必须保持这一边界，不对未知目标保存目录通配授权。秘密通过既有 secret_env 通道传递，显示脱敏不应改变实际执行内容。避免另建绕过 requestApproval 的执行通路。

脚本入口在第一阶段可暂不实现，此时不合格复杂调用应被明确阻断；上线完整入口后才支持相应必要工作流。

### 5. 审批展示真实执行对象

普通操作优先展示操作、文件列表、工作目录与来源；保留完整原始参数供展开查看。已解析的目标和未解析表达式分开展示，不能用 known 目录暗示它覆盖了未知写入。

脚本审阅不能依靠截断的一行文本。窄终端、长路径、Unicode、控制字符和凭据都需要专门处理；无法提供完整审阅时不能提供具有误导性的 Allow once。

## 实施阶段及交付

### 阶段一：建立不会耗尽后放行的约束

1. 在现有 assessment 上拆分 advisory 和强制决策，补充原因码。
2. 修改 command_preflight.go 的 used 逻辑和请求级纠正预算，接入终止状态与清晰错误。
3. 在 request_session.go 保持每次执行前检查；确保缓存、并行调用、Minimal、已保存规则及临时目录不会越过结构约束。
4. 更新旧设计文档，明确 never 和只读豁免的边界。
5. 用模拟工具记录证明连续不合格调用均执行零次，且纠正循环会停止。

交付标准：原始下载循环和等价 PowerShell 写法不能因第二次提交而进入普通审批。

### 阶段二：降低生成复杂命令的必要性

1. 补齐文件工具缺口，实现结构化批量下载。
2. 为 Shell 工具增加 cwd，复用统一规范化和授权逻辑。
3. 更新工具注册、描述和提示；遵守已有配置扩展要求，新增配置时同时维护结构、Help、模板和测试。
4. 下载场景改为“准备目录 → 下载列表 → 验证”，前置失败则不执行依赖步骤。

交付标准：8 个 Lua 文件可在三平台通过字面目标完成下载，无需 Shell 循环，也不会增加 8 次无意义确认；审批次数仍由现有临时目录和会话规则决定。

### 阶段三：覆盖解释器与完整脚本审阅

1. 完善 POSIX AST 和 PowerShell bridge 对嵌套执行、脚本文件及编码载荷的识别。
2. 对常见 Python、Node、编辑器求值等代码参数实施显式载荷识别；未知解释器保持未知，不伪装为已分析。
3. 增加完整脚本审阅、快照绑定和执行入口，覆盖拒绝、取消及内容变化。
4. 外部工具仅在可信执行能力契约下复用此机制；不靠工具名推断远端实现。

交付标准：把同一复杂操作搬到内联代码、临时文件或嵌套宿主，不能恢复普通命令审批。

### 阶段四：跨平台回归与发布验证

| 平台/模式 | 重点 |
| --- | --- |
| macOS、Linux 原生执行环境 | POSIX AST 与实际 Shell 匹配；循环、重定向、子 shell、路径展开、必要管道 |
| Windows PowerShell 5.1 | 原生 bridge、脚本块、编码执行、别名、Windows 路径和编码 |
| Windows PowerShell 7 | 同一语义样例与 5.1 决策一致；保留版本特有语法的明确差异 |
| 显式安装的其他 Shell | 识别宿主差异；无法可靠分析时不按已支持语法放行 |
| 模式与运行条件 | auto/always/never、Minimal、非交互、临时目录、保存规则、并发、请求恢复 |

必测场景：原始下载命令、合法只读过滤、长但简单的 argv、路径含空格/中文/美元符号、UNC 与驱动器路径、符号链接/重解析点、解析器失败、HTTP 失败与重定向、取消、批次部分失败、脚本审阅后变化、凭据脱敏。

测试分层：分析器表驱动测试；preflight 的零执行和重试上限测试；模拟模型改写的端到端测试；本地 HTTP 测试服务验证下载；三平台真实进程测试。安全不变量使用确定性测试验证，真实模型生成质量另作抽样评估，不设随机 CI 门槛。

运行项目要求的 check、test；安全相关包补充针对性的并发测试。扩展现有 build.yml/windows-reliability.yml 的平台矩阵，显式验证 PowerShell 5.1 和 7 都实际运行，不能把缺少宿主的 skip 当作通过。最终运行 CI 同等检查并构建二进制进行交互验收。

## 完成条件

- 不合格命令不会因为纠正预算用尽而执行或进入普通审批。
- 静态证明只读的合法命令仍免审，必要管道和单程序构建测试可用。
- 相同语义的 POSIX/PowerShell 命令得到一致的决策。
- 批量下载能完成实际任务，失败与部分结果可见。
- 复杂脚本的实际内容可审阅，执行与所审内容绑定，未知副作用不被隐去。
- 默认模式、显式 never、外部工具及非沙箱能力的保证边界有准确说明。

建议顺序：先完成阶段一和二，直接解决此次问题，再完成完整脚本入口。固定循环目标推导可以后续提升解释质量，但不能替代执行约束。
