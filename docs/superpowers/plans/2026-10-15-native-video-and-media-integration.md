# 原生视频处理与统一媒体链路计划

日期：2026-10-15。状态：已实施，验证记录见文末。基于工作区图片/音频版本扩展，保留现有未提交修改；未更改用户配置，未提交或推送。

## 目标与首版范围

用户通过一句话让 mods 扫描目录，直接将视频交给当前模型理解画面、可见文字和声音。可与图片、音频交叉核对，返回路径、证据和估计时间段。

支持的用法：

```sh
mods -a qwen -m qwen3.8-omni-flash '找出当前目录及子目录里提到退款的视频，列出路径、原话和大致时间段'
mods -a qwen -m qwen3.8-omni-flash --video meeting.mp4 --image slide.png '核对视频中的金额与图片是否一致'
```

首版以本地短 MP4 为范围，先支持普通非分片 MP4、H.264 视频轨和可选 AAC 音轨；具体可接受编码在协议探测后固定。无音轨视频可正常分析画面。输出文本，不包含录屏、摄像头、实时流、剪辑、视频生成或自动上传外部存储。

不默认将视频拆成图片再另做 ASR：优先发送原视频，保留声画时间关系。超限或不支持的文件明确报告未处理，不静默去掉声音、截断内容或转码。

## 已核实事实与尚待验证项

- [Qwen-Omni 调用指南](https://help.aliyun.com/zh/model-studio/qwen-omni)给出 Chat 的 `video_url.url` 以及本地视频 Base64 data URL 示例；音频和视频的 Base64 字符串要求小于 10MB。公网 URL 的长视频上限不能套用到本地内联请求。
- [Responses 接口](https://help.aliyun.com/zh/model-studio/qwen-api-via-openai-responses)列出 user 消息中的 `input_video`、`video_url` 和可选数字 `fps`。当前文档对该字段明确描述的是视频 URL；不能只凭 Chat 的本地示例推定 Responses 同样接受 data URL。
- 实施第一步用生成的非隐私小视频验证当前实际 Qwen 端点：Chat 本地输入、保留声音、工具后续轮次；Responses 的本地输入、字段和工具续接另测。单独输入成功不能替代工具回传验收。
- 视频混合图片/音频、多视频、thinking 状态续传和 fps 的字段位置、取值分别验证。没有证据的组合不宣称支持；未通过的 endpoint 不注册视频能力，并在显式输入时提前解释。不得为了通过测试改动用户默认 endpoint 或自动上传文件。

## 1. 扩展统一附件，而非增加平行的视频系统

修改 `internal/proto/media.go`：

- `MediaAttachment.Kind` 增加 video，增加具体 `VideoMetadata`，保存容器、视频/音频编码、时长、展示宽高、旋转、是否含音轨和选用的采样参数。源帧率与模型采样 fps 分开；可变帧率不能用帧数除以固定帧率冒充精确时长。
- 继续使用 Media 的有序附件、Source 和工具调用 ID 绑定来源。不另建 Videos 数组；不把一个视频同时存成原视频、帧图片和完整音频三份。
- 原 `Images` 兼容读取、规范化幂等、检查点字节深拷贝继续有效。新增元数据使用具体值类型，便于 gob 持久化，预计无须 SQLite 表迁移。
- 将现有 HasAudio 专用门控扩展为公共的模态校验。明确校验 image/audio/video，未识别模态报错。尤其替换 provider 编码器中“非 audio 就当 image”的分支，避免视频误编码成图片。

## 2. 在原有工具上增加 video

修改 `internal/tools/media_tools.go`、共享扫描器及 `internal/tooling`：

- `fs_find_media` 的 kinds 支持 image/audio/video，返回候选路径、类型、游标和扫描问题。游标绑定规范化的完整 kinds 集合；过滤顺序不影响范围判断。保持隐藏目录、取消、目录变化检查及不跟随目录符号链接的行为。
- `fs_read_media` 读取混合附件，视频首版每次最多 1 个；现有每次最多 8 个媒体及 4 个音频限制继续生效。图片别名仍只接受图片。
- 候选发现包含 MP4 及常见其他视频后缀（如 MOV/MKV/WebM/AVI），读取时按真实容器与轨道决定支持与否。暂不支持者列为 unread，不能计入“检查后不匹配”。扩展名不决定 MIME 或音视频类型，音频专用 MP4/M4A 不误当作有画面的视频。
- 识别“视频、录像、录屏、video、clip、.mp4”等自然语言意图；filesystem=never 保持有效。
- 使用既有只读审核、外部路径授权和工具表，不新增视频执行器或特例权限。能力门控同步影响工具 schema、说明及实际执行。
- 扫描/读取完成度仍表示文件发现和附件送达，不表示每一帧均被观看。输出必须说明采样可能遗漏短暂内容；未命中、无法判断、未读取分别报告。JSON 模式诊断继续走独立通道。

## 3. 本地视频读取和元数据

新增 `internal/video`，抽取现有 `readAttachment` 的媒体识别职责：

- 采用经过评估的 Go MP4 容器解析库，固定版本；优先保持产品无需 ffmpeg/ffprobe/Python。选库条件包括跨平台、许可证、维护状态、大小限制及能否安全读取轨道与时长。若无法满足首版，收窄格式范围并在实施记录说明，不自行草率实现完整 MP4 解析器。
- 普通文件检查、限量读取、取消检查，随后按 magic/container/track 识别。对 ISO BMFF 不能只看 ftyp：区分图片容器、音频文件和视频轨。先拒绝超限文件，避免完整解析或编码大文件。
- 支持 moov 在前/后的常见 MP4；检查 box 长度、越界、扩展大小、轨道引用、时基、展示旋转、异常分辨率及空媒体数据。碎片化、加密、未知编码和不明确时长首版明确拒绝。
- 容器校验不等于完整视频解码验证。模型端解码失败仍应显示为未处理；本地不要宣称已验证每帧完整性。
- 音轨存在不代表一定有语音；无音轨、静音、噪声与不可解码音轨分别处理，不能默默降级为仅看画面。

## 4. Qwen 编码、能力和工具回传

修改 `internal/stream` 能力契约和 `internal/openai`：

- 能力至少区分视频直接输入、工具回传、是否可用视频声音及混合输入；沿用现有明确模型/endpoint 识别，避免仅凭 OpenAI 兼容协议给所有模型开视频。
- Chat 使用经验证的 video 内容块；Responses 使用其 input_video 字段。采样参数位置与本地 data URL 形状以实际探测为准，不复用音频字段。
- 继续 `ProjectToolMedia`：完整 tool 结果组后追加带来源标签的 user 媒体，只存在于发送投影，不写成新的真实用户指令。记录、重试、继续会话时不重复投影。
- 保留 Qwen reasoning/usage 及独立续传状态；不得影响其他供应商已有图片编码。所有其他适配器在初始请求和后续工具轮次都明确拒绝未支持的视频，不能静默过滤。
- 若 Responses 本地视频验证失败，首版 Chat 可独立交付，文档和能力准确标注限制，不自动切换用户路由。

## 5. 共用预算，加上视频时间和采样成本

扩展 `ValidateMedia`、`ValidateMediaWireRequest` 和工具预算状态，不给视频另开一份 20 MiB：

| 预算 | 首版建议的产品限制（不是供应商上限） |
| --- | --- |
| 所有媒体原始字节 | 仍共用 20 MiB，包含 CLI、历史和工具结果 |
| 最终编码请求 | 仍为 40 MiB，并服从更小的 endpoint 限制 |
| 单视频原始大小 | 暂定 6 MiB；仍检查实际 Base64/data URL 大小小于供应商限制 |
| 单视频时长 | 暂定 2 分钟 |
| 上下文视频总时长 | 暂定 5 分钟 |
| 每次工具读取视频数量 | 1 个 |
| 默认采样 | 优先验证 2 fps；参数不支持时按已验证的服务端策略处理，不能声称固定抽帧 |
| 展示分辨率/采样量 | 暂定不超过 1080p；按实际 fps 估算每文件最多 600 帧、上下文最多 1200 帧，探测后固化 |

上述限制取交集，文件大小可能先触发。采样估计不能替代供应商 token/像素限制；如果接口具有自适应抽帧，需要按其实际参数设计保守估计或收窄输入范围。源视频高 fps 不等于发送模型的采样 fps。

含音轨的视频只计算一次原始字节，同时计入视频时长和已有 15 分钟音频时间预算；单独音频与视频音轨不能绕过累计时间限制。已有图片数量/像素、单音频大小/时长限制不变。每次读取预留预算，发送前重新校验，历史同样计量。

首版先采用已验证的固定采样策略，避免提前新增未经证实的调优配置。可调 fps、降分辨率和转码留给后续明确设计；任何变换都要保存实际参数与来源映射。

## 6. CLI、会话与帮助

- 增加可重复 `--video PATH`，允许与 --image、--audio 组合；属于本次输入参数，不持久化为配置默认值，不增加 stdin-video。
- CLI 与工具读取复用视频校验、元数据和预算。先检查模型/endpoint 能力，再读取和发送；保存会话包含原字节，恢复不重新打开源文件。
- 更新 flags 单点声明、Help、自帮助、README、AGENTS 和必要配置示例；无新持久化配置时不增加多余配置项。
- transcript/session viewer 显示来源、容器、时长、分辨率、是否有音轨与采样信息，不显示 Base64。时间段属于模型估计，无帧级对齐能力时不得标为精确定位。

## 后续阶段：长视频

长视频需要联合设计分段读取、重叠窗口、原视频时间轴偏移、证据去重、进度恢复，以及旧媒体上下文回收。只循环发送片段会持续累积历史，不能解决容量问题。届时再评估 ffmpeg 的显式依赖和转码策略；用户授权的外部存储/URL 输入另立方案，不自动上传本地文件。


## 实施与验证记录

- 统一附件新增 VideoMetadata；`--video`、目录发现/读取、历史恢复、来源标签、能力校验与混合预算已接通。原图片别名保持只读图片。
- 使用 MIT 许可的 `github.com/abema/go-mp4 v1.7.3`，纯 Go 解析有界非分片 MP4。首版严格要求一个 avc1 视频轨和可选一个 AAC-LC 音轨、普通时间轴、内部数据引用；不承诺完整解码检查。依赖不调用外部程序。
- Chat 和 Responses 分别用生成的非隐私视频验证：本地 data URL、fps 字段、单视频画面文字和声音识别、工具续接、图片+音频+视频混合请求均成功。视频画面为 ORCHID 5826 / $99，声音为退款编号 7341 / $42。恢复已保存会话后，即使源视频路径不存在，仍正确识别原声画。
- 多视频自然语言目录检索已跑通递归发现、每次一个视频、无声视频及完整附件续传，但供应商模型的答案质量不稳定：曾漏听音轨、编造引文、混淆退款与报销，或提前输出进度。补充了音轨存在标记、逐文件先记录证据再读取下一个文件、声画分开和抽帧覆盖说明；这些提示不能保证识别准确率。不得把读取成功统计当成识别成功，也不能把单文件正确结果宣传成批量检索准确率保证。
- 本地验证覆盖损坏/加密/分片/伪装扩展名、旋转、无音轨、moov 在尾部、取消、混合预算、目录游标/隐藏目录、外部只读权限、两协议工具消息顺序、能力拒绝和会话往返。全量 check/test、相关包 race、10 秒 MP4 fuzz（15900 次执行）通过；macOS 构建及 Linux/Windows 交叉编译通过。
- 二进制测试样本仅包含自生成文字、色块和合成语音；运行测试不需要 ffmpeg。长视频、自动转码、精确逐帧检索、自动上下文压缩仍不在首版范围。
