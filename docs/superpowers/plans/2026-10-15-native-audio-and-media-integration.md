# 原生音频处理与图片整合计划

日期：2026-10-15。状态：首版已实施。以下保留设计依据，实际交付与验证记录见文末；用户配置未修改。

## 目标

沿用图片功能的使用方式，让当前模型通过工具直接接收音频，并能联合理解图片与音频。目标示例（计划中的能力）：

```sh
mods -a qwen -m qwen3.8-omni-flash '找出当前目录及子目录里提到退款的录音，列出路径和听到的原话'
mods -a qwen -m qwen3.8-omni-flash '总结 meeting.wav，并核对 slide.png 中的数字是否与录音一致'
mods -a qwen -m qwen3.8-omni-flash --audio meeting.wav --image slide.png '整理会议结论和图片中的待办事项'
```

首版支持音频内容检索、转写、总结、声音事件描述，以及图音联合问答。模型直接听音频，不默认走外部 ASR、Python 脚本或嵌套启动 mods。转写是可选任务，不是所有音频理解任务的强制中间步骤。

首版不包含麦克风录音、实时语音会话、语音合成、播放、音频编辑、视频及自动上传外部存储。长录音分段作为后续阶段，不把一次能够处理短录音宣传成不限长度的目录处理。

## 已核实依据

- 当前用户配置在 qwen provider 下声明的是 `qwen3.8-omni-flash`，与官方模型 ID 一致。使用 `dashscope.aliyuncs.com/compatible-mode/v1`，该条目没有显式 endpoint；按现有代码会走 Chat Completions。规划时只查看模型及端点字段；实施时使用生成的非隐私媒体做了真实接口验证，未改用户配置。
- [官方模型说明](https://help.aliyun.com/zh/model-studio/qwen3-8-omni-flash)：支持图片、音频输入和 Function Calling，输出为文本；不要混同 Realtime 或其他 Omni 型号的语音输出能力。
- [官方调用指南](https://help.aliyun.com/zh/model-studio/qwen-omni)：Chat Completions 使用 `input_audio` 内容块；本地文件示例采用 `input_audio.data` 中的 Base64 data URL 和 format。Responses 音频字段形状不同，音频只能放在 user 消息中。文档也给出了图片与音频一起输入的示例。
- 同一指南把本地音频 Base64 字符串限制为小于 10MB；公网 URL 的大小/时长上限不能用于判断本地内联文件是否可发送。实现前按实际地域和端点复核边界。

这些文档事实只用于确定协议方向。当前用户端点的图音混合、多音频、工具回传及思考状态续传，要在第一阶段做小样本真实验证，不凭“兼容 OpenAI”推定全部可用。

## 一、统一内部媒体表示，兼容现有图片

新增具体的 `proto.MediaAttachment`（名称可在实施时微调），而不是把 audio 塞进 Image，也不无限增加 Images/Audios/Videos 平行处理分支。

建议字段：Kind、Data、MIMEType、Source、ID，以及可选的音频元数据结构（Container、Codec、DurationMillis、SampleRate、Channels）。来源绑定必须稳定，多个附件保持顺序，不能把全部图片和全部音频各自排序后丢失对应关系。暂不增加任意 `map[string]any` 元数据或混杂的接口类型，以便 gob 兼容。

Message 与 ToolResult 增加有序 Media 字段。规范化访问函数统一供 provider、预算、转录显示和持久化调用：

- 新代码只写 Media；现有 Images 字段保留为旧会话读取入口。
- 在会话加载/请求规范化边界将旧 Images 转成媒体，不同时保留两份字节副本。重复规范化必须幂等。
- 若输入同时出现旧、新字段，制定明确的合并和重复判断规则，不能静默丢掉不同附件，也不能重复发送同一附件。
- 保留现有工具结果 ID、错误状态与文本调用兼容接口。普通文本工具无须改签名。
- 默认不改 SQLite 表结构；如果只是 gob 增加字段，使用向后兼容测试证明旧会话可读。新版音频会话不承诺能被旧版程序完整理解。

第一步先把图片全链路迁移到公共访问函数并通过现有图片测试，再接音频，避免同时引入两类故障。

## 二、共用发现与读取工具

增加两个模型可调用的通用工具：

- `fs_find_media(path, kinds, recursive, cursor, limit)`：kinds 为 image/audio；返回候选路径、媒体类型、续页游标及扫描问题。扩展名用于候选筛选，真实格式由读取器校验。
- `fs_read_media(paths)`：识别真实格式，返回有序媒体附件和逐文件状态。支持一次读取图片与录音；保留文件来源标签，部分失败不丢掉成功附件。

保留 `fs_find_images`、`fs_read_images` 的原名称与参数，作为公共引擎的 image-only 包装，避免已发布功能和历史提示回归。不再复制一套 `fs_find_audio`/`fs_read_audio` 扫描和状态实现。

所有内置工具仍在 `builtinTools()` 单点声明；音频能力决定通用工具允许的 kinds，而不是让不支持音频的模型拿到可执行的音频读取入口。混合请求必须在真正读取前检查能力。不支持时给出明确的模型/端点说明，不静默删除音频。

保留现有只读授权语义、路径解析、隐藏目录、分页和目录变化检查。新增语音、音频、录音、audio、recording 等意图识别，filesystem=never 仍然生效。新媒体工具继续从写目标推断的发现工具集合中排除。

完成度区分“已发现”“已读取并送达模型”“读取失败”“尚未处理”。前两者不能当作识别准确率证明。混合文件来自同一共享跟踪器，不能图片显示完成、音频却被遗漏。机器可读输出模式下，未完成提示通过独立诊断通道显示并保存在会话中，不在 JSON 正文后拼接散文。

## 三、音频读取与明确的首版格式

首版完整支持 WAV（先限定常见 PCM 编码）与 MP3，覆盖真实 MIME/文件结构校验、时长、采样率和声道数。具体 Go 库在实施时按跨平台、维护状态与依赖大小选择；不为解析音频而引入 Python 环境或把 ffmpeg 设为默认运行前提。

WAV 解析应正确遍历 RIFF chunks，不能假定固定 44 字节头。MP3 要考虑 ID3、VBR 和损坏帧，不用文件字节数猜测时长。未知时长或编码必须明确报错/标记，不当作零时长通过限制。

读取普通文件、限制读取字节数，遵循取消与超时。文件名后缀不作为可信 MIME；不可读、空文件、伪格式、截断、超限均逐文件报告。保留原始字节，不默认转单声道、重采样或去噪，避免丢失音乐、环境声和空间信息；服务端是否按多声道解释属于独立能力。

AAC/M4A/FLAC/OGG 等列入后续格式扩展。候选扫描若识别出这些常见音频，应报告暂不支持，不能把它们算作已检查。时间戳输出首版只是模型估计；没有强制对齐能力时，不声称毫秒级定位。

## 四、Qwen 接入与模态级能力判断

首版以当前配置的 Chat Completions 为必达路径；同时规划显式 Responses 的适配，但不自动切换用户端点或改变 base-url。

能力信息至少表达：支持的输入模态、哪些模态可通过工具回传、每模态的投影方式、允许的混合组合及限制。沿用现有能力接口逐步扩展，不用一个 SupportsMultimodal 布尔值笼统判断。

| 模型/通道 | 音频工具结果如何进入后续请求 |
| --- | --- |
| Qwen Omni Chat Completions | 先返回本轮全部 tool 结果，再追加携带来源标签的 user 音频/图片内容块。音频使用 Qwen 对应的 input_audio 格式。 |
| Qwen Omni Responses | 同样在 tool 输出组完成后投影为 user 音频内容；使用 Qwen 的 Responses 字段。禁止因 DeepSeek 支持图片工具输出，就推定 Qwen 音频也支持原生工具输出。 |
| 已有 DeepSeek/OpenAI/Anthropic/Ollama 图片通道 | 保留其现有合法图片编码，不能统一强制改成 Qwen 的 wire format。 |
| 未适配的音频模型/端点 | 不注册可用音频能力；用户显式附音频时提前提示，而非转写成乱码或丢弃。 |

在 `internal/openai` 内按明确 provider/model/endpoint 选择音频编码器。若需要新增 Qwen provider profile，要检查当前 profile 枚举验证、配置向导、配置模板、自帮助及测试的全部入口；兼容传输类型 openai 不变。优先自动识别已知 qwen provider 与已配置模型，不要求用户为现有官方配置补必填字段。

工具派生的 user 附件只存在于发送投影中，不反写成新的真实用户需求；图片文字、录音中的指令均为待分析内容。多工具结果必须完整成组后才投影，同一附件在重试和会话恢复时不得被投影两遍。

验证 thinking 开关、reasoning_content 的续传要求、流式文本和 usage；不能直接沿用普通 qwen 模型或 DeepSeek 的思考参数规则。若 SDK 尚未覆盖所需内容块，采用局部、带请求体测试的编码扩展，不先做无关 SDK 大升级。

## 五、共享容量预算与长录音边界

把图片预算提升为公共 MediaBudget，仍保留图片专有的数量和像素限制。音频额外检查单文件时长、累计时长、单文件编码后大小、每轮数量；图音混合请求共同受原始字节和最终 wire body 大小约束。不能让图片和音频各自享有 20 MiB，最后叠加出一个未经校验的请求。

首版建议的产品侧保守预算（不是供应商能力上限，协议探测后再固化）：

- 沿用整个请求累计原始媒体 20 MiB、序列化请求 40 MiB 上限，并取实际供应商限制的更小值。
- 本地单音频暂设原始数据不超过 6 MiB，为 Qwen Base64 限制留余量；最终还必须对实际编码后的长度检查，而非只做估算。
- 音频每次读取建议 1～2 个，硬上限 4 个；每文件最长 10 分钟、上下文累计最长 15 分钟，且上述大小限制可能更早触发。图片工具现有 8 张批次与 64 张累计上限保留。
- 计算包含 CLI、工具结果、已保存历史和同轮多个工具调用；在接受附件时预留，在实际请求发送前再次检查。历史媒体与重复投影不能重复计费式地扣本地预算。

这些限制决定首版适合短音频处理。长录音、多文件大目录若超过预算，要报告覆盖范围和未处理文件，不截断后声称完整处理，也不自动上传用户音频来绕过限制。

第二阶段再实现按时段读取、重叠分段、全局时间偏移、去重合并、可恢复处理进度及上下文摘要。即使分段，旧音频仍会占用历史上下文；分段必须与明确的上下文回收/分批推理设计一起交付，不能只添加 chunk 循环。

## 六、CLI、会话与日志保持一致

- 增加可重复的 `--audio PATH`，与 `--image` 可组合。不占用已有 `-a`（api）。首版不增加 `--stdin-audio`，避免未经设计地改变管道文本语义。
- CLI 音频也进入公共媒体读取/校验和预算路径，不能与工具读取形成两套限制。
- 遵循 flags.go 单点声明、自帮助目录、Help 映射及配置覆盖测试；音频路径是本次请求参数，不自动变成持久化默认配置。
- 会话保存媒体字节、类型、来源和元数据；检查点深拷贝、--continue、transcript、session viewer 都理解混合媒体。继续会话使用保存的字节，不偷偷重新读取已经改变的源文件。
- CLI 展示路径、格式、时长、是否成功读取；日志和文本导出不出现 Base64。音频内容不能当作用户授权依据。
- 复用现有会话保存约定。更大的附件库、跨会话缓存和外部文件引用存储不在首版引入，避免同时改动数据库和附件生命周期。
